* Purpose

This is a document that describe the Tempo app from the product perspective. Its roadmap works as a
backlog because it holds the action items identified by the product manager; it works as a tracker
because its action items are toggleable todo items that should be marked as DONE when they get
implemented; and it works as a spec because the tests should prove the software satisfies the
requirements expressed in the [[*Features Overview][Features Overview]] and [[*Roadmap][Roadmap]].

This is the single source of truth for product work and specification.  Roadmap items are epics:
they only flip from TODO to DONE in place once fully delivered, and are never moved out of the
Roadmap. The [[*Changelog][Changelog]] accumulates independently — one entry per session or PR-sized unit of shipped
work, at whatever granularity that naturally comes in, so several Changelog entries can land under
one Roadmap epic before it's complete. A Changelog entry that contributes to a Roadmap item should
link back to it, e.g. "part of [[*Enable hourly rates and billing calculation for projects][Enable hourly rates and billing calculation for projects]]"; entries
with no matching epic just stand alone.

Features Overview in turn maps forward to the Roadmap epic(s) that deliver or harden each feature.
A feature entry should link to them, e.g. "delivered by [[*Offline support][Offline support]]" or "hardened by 
[[*Extend login session duration / reduce forced re-logins][Extend login session duration / reduce forced re-logins]]" — a feature can accumulate more than one 
epic link over time. Epics with no single shippable feature of their own (pure internal hardening 
with no new user-facing capability, or a cross-cutting packaging change like tiering) won't have a 
feature pointing back to them.

* Offline Support Design
:PROPERTIES:
:CREATED: [2026-08-13 Thu]
:END:
Design and tradeoff analysis backing [[*Offline support][Offline support]] in the Roadmap.

** Problem
The service worker added for [[*PWA support][PWA support]] only caches the static app shell (HTML/JS/CSS/icons), not
API data. Offline, the shell loads but every data request (session check, event list, timer stop)
fails — before this was diagnosed, a failed session check left the app on a blank screen
indefinitely, since nothing handled that state (fixed separately — see the Changelog). There is
currently no offline data story at all: no cached events to fall back to, and no way to create or
edit a session without a live round trip to the backend.

** Design decisions and tradeoffs

*** Persistence: IndexedDB, not React state or localStorage
In-memory state doesn't survive a page reload, a closed tab, or — especially relevant on mobile —
iOS evicting a backgrounded PWA's process to reclaim memory. Since going offline can mean hours
between "create a session" and "reconnect," anything queued for sync has to survive process death,
which rules out plain React state.

localStorage (already used by [[file:frontend/src/context/timer.tsx][context/timer.tsx]] to persist the currently-running timer) was
considered and rejected for the *queue and cache*, though it remains the right choice for that one
small object: it's synchronous (blocks the main thread), string-only (manual JSON (de)serialization
per record), capped around 5–10MB, and has no query/index support. IndexedDB is async, stores
structured objects natively, has a much larger origin-based quota, and supports indexed lookups —
needed once we're storing potentially hundreds of cached events plus an ordered mutation queue.

*** Sync trigger: 'online' event + on-load check, not the Background Sync API
The Background Sync API would let queued writes sync even after the tab is closed, but browser
support is inconsistent and notably weak/absent on iOS Safari — the platform this app is actually
installed on as a PWA today.  Syncing only while the app is open (on load, and on the browser's
'online' event) is simpler, more predictable, and doesn't silently depend on a capability that may
not exist on the user's device.

*** Conflict handling: surface and stop, no auto-merge
The backend rejects overlapping sessions server-side ([[file:backend/src/tracking/tracking.service.ts][tracking.service.ts]]'s assertNoOverlap). If a
queued item is rejected on sync (409 overlap, 404 not found because the referenced project or event
was deleted elsewhere, etc.), the queue stops draining at that item and the conflict is surfaced
clearly in the UI rather than dropped or auto-resolved. Tracking events are scoped per user account,
and each account is still only used by one person across their own devices (see README's Access
Control section), so building real multi-device merge logic isn't worth the complexity it would add
— a human resolving an occasional conflict manually is an acceptable tradeoff here.

*** Scope boundaries
Deliberately deferred or out of scope: offline *editing or deleting* of projects (only offline
*creation* is considered, and only in Phase 4 — see above); any cross-device automatic conflict
resolution; and the Background Sync API (see above).

* Login / Auth Design
:PROPERTIES:
:CREATED: [2026-08-19 Wed]
:END:
Design context backing [[*Extend login session duration / reduce forced re-logins][Extend login session duration / reduce forced re-logins]] in the Roadmap.

** Current architecture
Authentication is Google OAuth 2.0 via Passport ([[file:backend/src/auth/google.strategy.ts][google.strategy.ts]]), backed by a server-side
session — not a client-held JWT. The frontend never sees a token: it authenticates by sending the
`connect.sid` cookie automatically (`credentials: "include"` in [[file:frontend/src/api/client.ts][api/client.ts]]) and checks login
state by calling `GET /auth/me` on load ([[file:frontend/src/hooks/useAuth.ts][hooks/useAuth.ts]]). A confirmed 401 routes the user to
=/login=; a network/5xx error with a cached user instead shows a "can't reach Tempo" retry screen,
so being offline isn't confused with being logged out ([[file:frontend/src/layouts/AppLayout.tsx][AppLayout.tsx]]).

Sessions live server-side via `express-session` ([[file:backend/src/main.ts][main.ts]]), persisted to a SQLite file
(`connect-sqlite3`) in the same Docker volume as the app database, so a backend restart/redeploy no
longer wipes active sessions. The `connect.sid` cookie is `httpOnly`, `secure` in production, has a
7-day `maxAge`, and now uses `rolling: true` so active use keeps extending the cookie instead of
logging someone out mid-session. There is still no refresh-token mechanism (none needed — it's a
plain server session, not a JWT). Only `user_id` is serialized into the session
([[file:backend/src/auth/session.serializer.ts][session.serializer.ts]]); the full user is re-hydrated from the DB on every request. `SESSION_SECRET`
is now required in production — the process refuses to start rather than silently signing sessions
with a guessable default.

** Problem (resolved)
Users were being asked to log back in more often than the 7-day cookie lifetime alone would
suggest. The cause was that every backend restart/redeploy wiped the in-memory `memorystore` session
store, silently invalidating all sessions regardless of cookie age. This had already cost real data
once: a time-tracking session was lost when a forced re-login interrupted it. That incident predates
[[*Offline support][Offline support]], which would likely prevent a recurrence today by queuing the in-flight change
locally, but offline support didn't address the underlying cause of the frequent logouts
themselves. The app now has multiple real users (friends, not just the product owner — see README's
Access Control section), so an in-memory session store forcing everyone out on every redeploy was a
bigger blast radius than it used to be. Fixed by moving to a persistent SQLite-backed session store
— see the Changelog entry under [[*Extend login session duration / reduce forced re-logins][Extend login session duration / reduce forced re-logins]].

** Open questions
- Move to a persistent session store. The app currently runs on SQLite ([[file:backend/src/app.module.ts][app.module.ts]]), not
  Postgres, so the lowest-risk fix is a SQLite/TypeORM-backed session store (e.g.  `connect-sqlite3`
  or `connect-typeorm`) pointed at the same persisted Docker volume as the main DB — not a full
  migration to Postgres, which the README lists as a possible *future* infra change but which isn't
  needed just to fix session persistence.
- Consider extending `maxAge` and/or enabling rolling sessions so active use keeps extending the
  cookie lifetime.
- Access is optionally gated by a single `ALLOWED_EMAIL` ([[file:backend/src/auth/auth.service.ts][auth.service.ts]]); with actual friends
  using the app under their own Google accounts, revisit whether that single-email allowlist is
  still the right access control model, independent of the session-duration fix.

** Session store options: connect-sqlite3 vs connect-typeorm

Both point the session store at the same SQLite file already used for the app DB (persisted in the
existing Docker volume), so either fixes the restart/redeploy data loss. They differ in integration
style:

| | =connect-sqlite3= | =connect-typeorm= |
|---|---|---|
| Storage | Own SQLite file/table via its own =sqlite3= driver, independent of the app's =better-sqlite3=/TypeORM connection | Reuses the app's existing TypeORM =DataSource=, adds a =Session= entity managed by TypeORM |
| Maintenance | Actively published (0.9.18, released 2026-08-06) | Last published 2.0.0 in 2022-07-05; no activity since |
| Schema coupling | None — session table lives outside TypeORM's =synchronize: true= schema management | Session entity is subject to the same auto-sync as app entities ([[file:backend/src/app.module.ts][app.module.ts:26]]), so a bad synchronize run on app entities can't easily be isolated from session data |
| Dependencies added | =connect-sqlite3= + a second SQLite driver (=sqlite3=, separate from =better-sqlite3=) alongside the one already in use | No new SQLite driver; adds only the =connect-typeorm= package on top of the existing TypeORM setup |
| Types | =@types/connect-sqlite3= exists but lags (0.9.6 vs library 0.9.18) | Written in TypeScript, ships its own types |
| Failure isolation | A problem in the session store can't corrupt app data or vice versa (separate file/driver) | Session store shares fate with the app DB connection — one connection pool, one point of failure, but also one less moving part |

*Decision:* =connect-sqlite3=, mainly because =connect-typeorm= hasn't
been published since 2022 (this project is actively maintained and running
current dependency versions elsewhere), and keeping the session table outside
TypeORM's =synchronize: true= avoids any chance of app-entity schema changes
touching session data. The tradeoff is a second SQLite driver dependency and
slightly lagging community type definitions, both minor. Note: neither
option helps with running multiple backend replicas — both are SQLite-file
based, and a file can't be shared across containers. Sharing sessions across
replicas would need a network-accessible store (Postgres/Redis) regardless
of which of these two is picked now; that's out of scope here (see the
single-replica note in the Migration plan below).

** Migration plan (done)

- [X] Add =connect-sqlite3= (and =@types/connect-sqlite3=) to =backend/package.json=.
- [X] Point the store at a file inside the same persisted Docker volume the main DB already uses, so
  it survives restarts/redeploys the same way.
- [X] Swap =memorystore= for the new store in [[file:backend/src/main.ts][main.ts]], keeping the same cookie options.
- [X] Make =SESSION_SECRET= required in production instead of silently defaulting to a hardcoded
  string ("=change-me-in-production=", which was misleading since it named production but was only
  ever reachable outside it even before this fix — renamed to
  =local-dev-only-secret-not-for-production= for clarity) — bundled in here since it's touching the
  same session setup code (the broader hardening pass is tracked separately under [[*Harden auth/session security][Harden
  auth/session security]]).
- [X] Add =rolling: true= so active users don't get logged out mid-use before the 7-day mark.
- [X] Verify locally: log in, restart the backend process, confirm the session survives on the same
  cookie.
- [X] Update the README (Security section, and the "swap SQLite for Postgres" note that previously
  implied the session fix required a full DB migration).
- [X] Note the remaining limit: still single-replica only (a SQLite-file store can't be shared
  across multiple backend containers) — out of scope unless/until scaling beyond one container is

* Push Notifications Design
:PROPERTIES:
:CREATED: [2026-08-25 Tue]
:END:
Design and tradeoff analysis backing [[*Push notifications][Push notifications]] in the Roadmap.

** Problem
Features Overview promises push notifications "for reminders and events," but no reminder/goal
engine exists yet — [[*Set daily, weekly or monthly goals or budgets][Set daily, weekly or monthly goals or budgets]] and [[*Define repeatable tasks][Define repeatable
tasks]] are both still open. So Phase 1 has to ship the subscribe/send infrastructure without a real
reminder source to trigger off of, then attach one concrete trigger — a long-running-session nudge —
built from data that already exists ([[file:backend/src/database/entities/tracking-event.entity.ts][tracking-event.entity.ts]]), rather than waiting on those other
epics. Triggers tied to goals or recurring tasks become natural follow-ups once those epics land.

** Design decisions and tradeoffs

*** Delivery: Web Push, not a native wrapper
Considered wrapping the PWA in Capacitor to get real APNs/FCM push. Rejected for now: [[*Compatibility][Compatibility]]
already establishes the team doesn't have the bandwidth to build or maintain a native/hybrid app, and
Web Push already covers Android plus installed-PWA iOS (16.4+) with no app-store distribution or
native build pipeline required. Tracked separately as [[*Add native app support (Capacitor wrapper for iOS/Android)][Add native app support (Capacitor wrapper for
iOS/Android)]] in the Roadmap, tagged =:maybe:=, in case a real gap shows up later (push without the
PWA installed, or native-only UI needs).

*** Protocol: Web Push + VAPID, no third-party push vendor
The standard W3C Push API with VAPID-signed requests (via the =web-push= npm package) needs no
external account or vendor (Firebase, OneSignal) and adds only one new dependency — consistent with
how this app has generally avoided vendor lock-in where a standard protocol exists. Subscriptions are
stored per-user in the existing SQLite database, the same pattern already used for sessions.

*** Trigger source: backend cron scan, not a client-side timer
A client-side timer only fires while a tab is open, which defeats the purpose of push (the whole
point is reaching a closed app). A backend cron job (=@nestjs/schedule=) scanning for eligible
tracking events and sending via =web-push= works regardless of whether the client is open, matching
how sync and other background concerns already live server-side in this app.

*** iOS constraint
Web Push only works on iOS when the PWA is installed to the home screen (no push in a regular Safari
tab, and only iOS 16.4+). This needs to be surfaced in the opt-in UI copy itself, not just documented
here — otherwise a user who hasn't installed the app will see a toggle that silently does nothing.

* Compatibility
Tempo is a web application which can be used easily on mobile screens. It would be of great benefit
to have it as an app both in desktop and mobile devices, but the team currently doesn't have the
bandwidth to implement or maintain such varied implementations. For now, it will continue to be a
web application — the roadmap includes making it installable as a progressive web app on mobile
devices (see [[*Roadmap][Roadmap]]).

All three items fixed: (1) =/api/auth/logout= was a =@Get()= route despite its own doc comment
saying POST — a GET is a state-changing request triggerable cross-site (e.g. via an =<img>= tag),
and the frontend was navigating to it with a raw =window.location.href= rather than a fetch call.
Changed the route to =@Post()=, changed it to respond with JSON instead of a redirect (it's no
longer a browser navigation), and updated [[file:frontend/src/components/Sidebar.tsx][Sidebar.tsx]]'s two logout buttons to call the existing
=auth.logout()= API client method (itself switched to =POST=) and then hard-navigate to =/login=
afterward — a full reload rather than a client-side route change, since there's no shared auth
state elsewhere in the app to invalidate. (2) The session cookie had no =sameSite= at all. Added
=sameSite: "lax"= in [[file:backend/src/main.ts][main.ts]] — =lax= rather than =strict= because the Google OAuth callback is a
top-level cross-site redirect back into the app, which =strict= would drop the cookie on; frontend
and backend are always same-origin in practice (Vite proxy in dev, Caddy reverse-proxy in prod), so
=lax= combined with the app's already-restrictive CORS config (single allowed origin,
=credentials: true=) closes the practical CSRF gap without adding a separate CSRF token
middleware. (3) =SESSION_SECRET= only failed startup when =NODE_ENV=== exactly ="production"=,
silently falling back to a hardcoded string otherwise (unset =NODE_ENV=, a typo, staging, etc. all
sailed through). Removed the =NODE_ENV= gate entirely — =SESSION_SECRET= is now required
unconditionally, matching what the README already documented as a required variable for every
environment.

Added [[file:e2e/tests/auth.spec.ts][auth.spec.ts]] covering the fixed logout flow end to end (button click → session actually
destroyed server-side, not just a client-side redirect). It needed its own isolated browser context
rather than the suite's shared =page= fixture, since every other spec authenticates via the same
=.auth/user.json= storageState written once by =global-setup.ts= and a real logout permanently
destroys that session. First attempt at the isolated context got this wrong in a way worth noting:
=@playwright/test='s =browser= fixture merges the project's =use= config (including
=storageState: '.auth/user.json'=) into any =browser.newContext()= call for options you don't
explicitly override — overriding only =baseURL= still leaves the new context holding the *shared*
session cookie. Calling test-login on top of that triggers Passport's session-regenerate-on-login,
which destroys the pre-existing session as a side effect of creating the new one, permanently
breaking every other spec's session before the new test's own logout call even runs. Fix was to
also explicitly pass =storageState: { cookies: [], origins: [] }=.

rewriting any dependent queued event's =project_id= once the project synced — rejected as
unnecessary machinery (a new local-id namespace, dependency rewriting in =drainQueue=) for a rare
case. Second, moving creation to [[file:frontend/src/pages/ProjectsPage.tsx][ProjectsPage.tsx]] but still queuing it through the same
offline-queue infrastructure as tracking events — rejected because a queued-but-unsynced project
can't actually be used yet (the Timer's project picker only ever offers already-synced projects, and
nothing merges pending projects into it), so queuing bought nothing over just failing clearly and
retrying once back online.

What shipped instead needed no new queue infrastructure at all: a session can already be logged with
no project attached (offline-queueable via the existing Phase 2 event queue), and reattributing a
session to a project afterwards is already supported by Phase 3's offline-edit flow
(=queueEventUpdate=). So the realistic offline workflow — work without a project while offline,
create the project once back online, then edit the session(s) to attach it — was already fully
covered. This phase is therefore just a relocation: project creation moved off the Timer (removing
its inline "+ New" toggle and the =onProjectCreated= callback plumbing through [[file:frontend/src/pages/DashboardPage.tsx][DashboardPage.tsx]])
and onto ProjectsPage as its own explicitly online-only action, disabled with a clear inline message
(gated on the existing [[file:frontend/src/context/onlineStatus.tsx][useOnlineStatus]] context) rather than letting the user submit something
guaranteed to fail. No backend changes.

utils/offlineQueue.ts's queue now holds three op types instead of just creates: 'create' (unchanged
from Phase 2), 'update' (targets a real server-side event id with a full replacement payload), and

drainQueue() PATCHes or DELETEs accordingly, still stopping and recording a conflict on the first
real rejection (e.g. a 409 overlap or a 404 because the target was deleted elsewhere), per the same
"surface and stop" policy as Phase 2.
