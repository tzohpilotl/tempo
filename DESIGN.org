* Design

This is a document that describe the Tempo app from the product
perspective. Its roadmap works as a backlog because it holds the action items
identified by the product manager; it works as a tracker because its action
items are toggleable todo items that should be marked as DONE when they get
implemented; and it works as a spec because the tests should prove the software
satisfies the requirements expressed in the [[*Features Overview][Features Overview]] and [[*Roadmap][Roadmap]].

This is the single source of truth for product work and specification.
Roadmap items are epics: they only flip from TODO to DONE in place once fully
delivered, and are never moved out of the Roadmap. The [[*Changelog][Changelog]]
accumulates independently — one entry per session or PR-sized unit of shipped
work, at whatever granularity that naturally comes in, so several Changelog
entries can land under one Roadmap epic before it's complete. A Changelog
entry that contributes to a Roadmap item should link back to it, e.g. "part of
[[*Enable hourly rates and billing calculation for projects][Enable hourly
rates and billing calculation for projects]]"; entries with no matching epic
just stand alone.

** Offline Support Design
:PROPERTIES:
:CREATED: [2026-08-13 Thu]
:END:
Design and tradeoff analysis backing [[*Offline support][Offline support]] in the Roadmap.

*** Problem
The service worker added for [[*PWA support][PWA support]] only caches the static
app shell (HTML/JS/CSS/icons), not API data. Offline, the shell loads but every
data request (session check, event list, timer stop) fails — before this was
diagnosed, a failed session check left the app on a blank screen indefinitely,
since nothing handled that state (fixed separately — see the Changelog). There
is currently no offline data story at all: no cached events to fall back to,
and no way to create or edit a session without a live round trip to the
backend.

*** Design decisions and tradeoffs

**** Persistence: IndexedDB, not React state or localStorage
In-memory state doesn't survive a page reload, a closed tab, or — especially
relevant on mobile — iOS evicting a backgrounded PWA's process to reclaim
memory. Since going offline can mean hours between "create a session" and
"reconnect," anything queued for sync has to survive process death, which
rules out plain React state.

localStorage (already used by [[file:frontend/src/context/timer.tsx][context/timer.tsx]]
to persist the currently-running timer) was considered and rejected for the
*queue and cache*, though it remains the right choice for that one small
object: it's synchronous (blocks the main thread), string-only (manual JSON
(de)serialization per record), capped around 5–10MB, and has no query/index
support. IndexedDB is async, stores structured objects natively, has a much
larger origin-based quota, and supports indexed lookups — needed once we're
storing potentially hundreds of cached events plus an ordered mutation queue.

**** Sync trigger: 'online' event + on-load check, not the Background Sync API
The Background Sync API would let queued writes sync even after the tab is
closed, but browser support is inconsistent and notably weak/absent on iOS
Safari — the platform this app is actually installed on as a PWA today.
Syncing only while the app is open (on load, and on the browser's 'online'
event) is simpler, more predictable, and doesn't silently depend on a
capability that may not exist on the user's device.

**** Conflict handling: surface and stop, no auto-merge
The backend rejects overlapping sessions server-side
([[file:backend/src/tracking/tracking.service.ts][tracking.service.ts]]'s
assertNoOverlap). If a queued item is rejected on sync (409 overlap, 404 not
found because the referenced project or event was deleted elsewhere, etc.),
the queue stops draining at that item and the conflict is surfaced clearly in
the UI rather than dropped or auto-resolved. Tracking events are scoped per
user account, and each account is still only used by one person across their
own devices (see README's Access Control section), so building real
multi-device merge logic isn't worth the complexity it would add — a human
resolving an occasional conflict manually is an acceptable tradeoff here.

**** Scope boundaries
Deliberately deferred or out of scope: offline *editing or deleting* of
projects (only offline *creation* is considered, and only in Phase 4 — see
above); any cross-device automatic conflict resolution; and the Background
Sync API (see above).

** Login / Auth Design
:PROPERTIES:
:CREATED: [2026-08-19 Wed]
:END:
Design context backing [[*Extend login session duration / reduce forced re-logins][Extend login session duration / reduce forced re-logins]] in the Roadmap.

*** Current architecture
Authentication is Google OAuth 2.0 via Passport
([[file:backend/src/auth/google.strategy.ts][google.strategy.ts]]), backed by
a server-side session — not a client-held JWT. The frontend never sees a
token: it authenticates by sending the `connect.sid` cookie automatically
(`credentials: "include"` in
[[file:frontend/src/api/client.ts][api/client.ts]]) and checks login state by
calling `GET /auth/me` on load
([[file:frontend/src/hooks/useAuth.ts][hooks/useAuth.ts]]). A confirmed 401
routes the user to =/login=; a network/5xx error with a cached user instead
shows a "can't reach Tempo" retry screen, so being offline isn't confused
with being logged out
([[file:frontend/src/layouts/AppLayout.tsx][AppLayout.tsx]]).

Sessions live server-side via `express-session`
([[file:backend/src/main.ts][main.ts]]), persisted to a SQLite file
(`connect-sqlite3`) in the same Docker volume as the app database, so a
backend restart/redeploy no longer wipes active sessions. The `connect.sid`
cookie is `httpOnly`, `secure` in production, has a 7-day `maxAge`, and now
uses `rolling: true` so active use keeps extending the cookie instead of
logging someone out mid-session. There is still no refresh-token mechanism
(none needed — it's a plain server session, not a JWT). Only `user_id` is
serialized into the session
([[file:backend/src/auth/session.serializer.ts][session.serializer.ts]]); the
full user is re-hydrated from the DB on every request. `SESSION_SECRET` is
now required in production — the process refuses to start rather than
silently signing sessions with a guessable default.

*** Problem (resolved)
Users were being asked to log back in more often than the 7-day cookie
lifetime alone would suggest. The cause was that every backend
restart/redeploy wiped the in-memory `memorystore` session store, silently
invalidating all sessions regardless of cookie age. This had already cost
real data once: a time-tracking session was lost when a forced re-login
interrupted it. That incident predates
[[*Offline support][Offline support]], which would likely prevent a
recurrence today by queuing the in-flight change locally, but offline
support didn't address the underlying cause of the frequent logouts
themselves. The app now has multiple real users (friends, not just the
product owner — see README's Access Control section), so an in-memory
session store forcing everyone out on every redeploy was a bigger blast
radius than it used to be. Fixed by moving to a persistent SQLite-backed
session store — see the Changelog entry under
[[*Extend login session duration / reduce forced re-logins][Extend login
session duration / reduce forced re-logins]].

*** Open questions
- Move to a persistent session store. The app currently runs on SQLite
  ([[file:backend/src/app.module.ts][app.module.ts]]), not Postgres, so the
  lowest-risk fix is a SQLite/TypeORM-backed session store (e.g.
  `connect-sqlite3` or `connect-typeorm`) pointed at the same persisted
  Docker volume as the main DB — not a full migration to Postgres, which
  the README lists as a possible *future* infra change but which isn't
  needed just to fix session persistence.
- Consider extending `maxAge` and/or enabling rolling sessions so active use
  keeps extending the cookie lifetime.
- Access is optionally gated by a single `ALLOWED_EMAIL`
  ([[file:backend/src/auth/auth.service.ts][auth.service.ts]]); with actual
  friends using the app under their own Google accounts, revisit whether that
  single-email allowlist is still the right access control model, independent
  of the session-duration fix.

*** Session store options: connect-sqlite3 vs connect-typeorm

Both point the session store at the same SQLite file already used for the
app DB (persisted in the existing Docker volume), so either fixes the
restart/redeploy data loss. They differ in integration style:

| | =connect-sqlite3= | =connect-typeorm= |
|---|---|---|
| Storage | Own SQLite file/table via its own =sqlite3= driver, independent of the app's =better-sqlite3=/TypeORM connection | Reuses the app's existing TypeORM =DataSource=, adds a =Session= entity managed by TypeORM |
| Maintenance | Actively published (0.9.18, released 2026-08-06) | Last published 2.0.0 in 2022-07-05; no activity since |
| Schema coupling | None — session table lives outside TypeORM's =synchronize: true= schema management | Session entity is subject to the same auto-sync as app entities ([[file:backend/src/app.module.ts][app.module.ts:26]]), so a bad synchronize run on app entities can't easily be isolated from session data |
| Dependencies added | =connect-sqlite3= + a second SQLite driver (=sqlite3=, separate from =better-sqlite3=) alongside the one already in use | No new SQLite driver; adds only the =connect-typeorm= package on top of the existing TypeORM setup |
| Types | =@types/connect-sqlite3= exists but lags (0.9.6 vs library 0.9.18) | Written in TypeScript, ships its own types |
| Failure isolation | A problem in the session store can't corrupt app data or vice versa (separate file/driver) | Session store shares fate with the app DB connection — one connection pool, one point of failure, but also one less moving part |

*Decision:* =connect-sqlite3=, mainly because =connect-typeorm= hasn't
been published since 2022 (this project is actively maintained and running
current dependency versions elsewhere), and keeping the session table outside
TypeORM's =synchronize: true= avoids any chance of app-entity schema changes
touching session data. The tradeoff is a second SQLite driver dependency and
slightly lagging community type definitions, both minor. Note: neither
option helps with running multiple backend replicas — both are SQLite-file
based, and a file can't be shared across containers. Sharing sessions across
replicas would need a network-accessible store (Postgres/Redis) regardless
of which of these two is picked now; that's out of scope here (see the
single-replica note in the Migration plan below).

*** Migration plan (done)

- [X] Point the store at a file inside the same persisted Docker volume the

  [[file:backend/src/main.ts][main.ts]], keeping the same cookie

  =local-dev-only-secret-not-for-production= for clarity) — bundled in
  here since it's touching the same session setup code (the broader
  hardening pass is tracked separately under
  [[*Harden auth/session security][Harden auth/session security]]).
- [X] Add =rolling: true= so active users don't get logged out mid-use
  before the 7-day mark.
- [X] Verify locally: log in, restart the backend process, confirm the

- [X] Update the README (Security section, and the "swap SQLite for

** Compatibility
Tempo is a web application which can be used easily on mobile screens. It would
be of great benefit to have it as an app both in desktop and mobile devices, but
the team currently doesn't have the bandwidth to implement or maintain such
varied implementations. For now, it will continue to be a web application — the
roadmap includes making it installable as a progressive web app on mobile
devices (see [[*Roadmap][Roadmap]]).

*** DONE Phase 3 — Offline edit/delete of existing events
:PROPERTIES:
:CREATED: [2026-08-18 Tue]
:END:
Part of [[*Phase 3 — Offline edit/delete of existing events][Phase 3 — Offline
edit/delete of existing events]] under [[*Offline support][Offline support]].

utils/offlineQueue.ts's queue now holds three op types instead of just
creates: 'create' (unchanged from Phase 2), 'update' (targets a real
server-side event id with a full replacement payload), and 'delete' (targets
a real server-side event id). Old Phase 2 entries predate the 'type' field —
getAllEntries() treats a typeless entry as a create for backward
compatibility. queueEventUpdate/queueEventDelete special-case editing or
deleting an event that is itself still a queued, not-yet-synced Phase 2
creation (a local-<uuid> id): there's nothing server-side to target yet, so
an edit is folded straight into the 'create' entry's payload (replacing it
entirely — only the final desired state matters) and a delete just drops
that 'create' entry from the queue outright, rather than ever producing a
separate 'update'/'delete' op with a local id as its target. A second edit to
the same already-synced target before the first one drains also replaces the
queued 'update' payload rather than stacking a second op; a delete queued
after a pending update drops that update first, since it's moot once the
event is gone. This means by the time drainQueue() runs, every 'update' and
'delete' entry is guaranteed to carry a real server id — drainQueue() PATCHes
or DELETEs accordingly, still stopping and recording a conflict on the first
real rejection (e.g. a 409 overlap or a 404 because the target was deleted
elsewhere), per the same "surface and stop" policy as Phase 2.

SyncConflict dropped its `event` field — update/delete conflicts have no full
TrackingEvent to show (only a patch or a bare id), and the banner only ever
rendered `conflict.error.message` anyway.

DashboardPage and SessionsPage's onUpdate/onDelete now mirror Timer.tsx's
Phase 2 pattern: an edit/delete on a still-local-only event goes straight to
queueEventUpdate/queueEventDelete (online or offline — there's no server
copy to call), and one on a real synced event tries the real PATCH/DELETE
first, falling back to the queue only on a network-level failure (a real
ApiError, e.g. an overlap or validation error, still surfaces as today).

Added getPendingChanges() (creates/updates/deletes snapshot) and
applyPendingChanges() (filters queued deletes and overlays queued edits onto
a fetched list, resolving project_id against the caller's already-loaded
projects rather than the response cache) to utils/offlineQueue.ts, and wired
both pages through them. This finally gives SessionsPage the pending-merge
DashboardPage got in Phase 2 (deferred at the time — see that entry below):
pending *creates* are only merged onto an unfiltered page 1, since a brand
new session has no real position in a paginated/filtered server list, but
pending *edits and deletes* apply regardless of page or filter, since the
event they target can be sitting anywhere. getPendingEvents() was renamed to
getPendingCreates() to make that distinction explicit now that "pending"
covers three different kinds of change.

Extended offlineQueue.test.ts with cases for both queue-folding behaviors
(edit/delete of a still-queued creation), update/delete op upserts and their
drainQueue POST/PATCH/DELETE dispatch, and applyPendingChanges' filter+patch
behavior. Added three e2e cases to offline.spec.ts: editing a synced session
offline, deleting one offline, and editing a session that is itself still an
unsynced creation — all asserting the change survives a reload once
reachable again. Also renamed the existing "N session(s) pending sync"
wording to "N change(s) pending sync", since the indicator now counts edits
and deletes too, not just new sessions — matching the "N pending changes"
phrasing this indicator was described with when first introduced in Phase 2
above.

*** DONE Phase 2 — Offline session creation
:PROPERTIES:

Part of [[*Phase 2 — Offline session creation][Phase 2 — Offline session

Added utils/offlineQueue.ts — its own IndexedDB database (separate from the
Phase 1 response cache; different concern, a durable ordered write queue, not
a keyed response cache). queueEventCreate() stores a pending create and
returns an optimistic TrackingEvent immediately (local-<uuid> id, project
name resolved from the Phase 1 projects cache). getPendingEvents() lets pages
merge not-yet-synced events into what they render, including after a reload.
drainQueue() is the sync engine: POSTs queued items in order, stops at the
first real rejection (ApiError, e.g. a 409 overlap) and records it as a
conflict rather than dropping or skipping it — the documented "surface and
stop" policy — and stops silently on a renewed network failure to retry
later. Guarded against concurrent calls, since two drains running at once
could double-POST the same item.

Timer.tsx's handleStop tries tracking.log() first; a real ApiError still
surfaces as today, but a network-level failure falls back to
queueEventCreate() instead, so the UI treats it as a normal save either way.
client.ts's request() is now exported so App.tsx can pass it into
drainQueue(), since synthesizing an optimistic response needs the raw
request — this couldn't be centralized inside request() itself the way
Phase 1's GET cache was, because building a valid optimistic TrackingEvent
needs domain knowledge request() doesn't have. drainQueue() takes the
request function as a parameter (a RequestFn type it defines itself) rather
than importing client.ts directly, so offlineQueue.ts stays agnostic of that
module's concrete implementation — only ApiError is still imported, for the
conflict-detection instanceof check. Tests inject a mock function directly
instead of stubbing global fetch.

DashboardPage merges pending events into its list, deduplicating by
(started_at, stopped_at) against the synced list — needed because
drainQueue() can finish syncing an item in the background between this
page's own fetch and its queue read finishing, which could otherwise show
the same session twice. SessionsPage does NOT get this merge — doing it
correctly there means reasoning about pagination and project-filter
interaction (pending events only make sense on page 1, unfiltered), which
felt like real scope creep for a secondary page when the primary surface
(Dashboard, where the Timer lives) was already covered; Phase 3 already
needs to handle "this event is still local-only" more deeply for edit/delete,
so consolidating that there is more honest than a partial fix now.

The sync trigger (App.tsx's QueueSync) originally only reacted to
navigator.onLine's 'online' event — but per the same navigator.onLine gap
already identified for the banner, that event doesn't fire when a dead
Wi-Fi uplink or throttled cellular data recovers either, so a drain could
get permanently stuck with no retry. Fixed by also reacting to
networkFailing (utils/networkStatus.ts) flipping back to false, which fires
whenever any request actually succeeds again, catching the case
navigator.onLine misses.

The offline banner (AppLayout.tsx) now reflects queue status too: pending
count while offline, "Syncing…" while online with items still draining, and
a distinct (danger-colored) message when drainQueue records a conflict.

Explicitly out of scope, matching what was already documented for this
phase: editing/deleting a still-queued event, and creating a *new* project
while offline as part of stopping the timer (that specific combined action
still fails with today's error message — queuing project creation is Phase 4
territory).
